# Phase 0 Validation Report — PR #1 (`feat/phase-0-milestones`, b25c990)

**Validator:** independent Claude instance (spec-author role), executable review in a clean sandbox.  
**Method:** cold clone, offline build (stdlib-only verified), full test suite, fuzz targets, determinism probe, and independent re-runs of the formal gate at multiple scales and seeds.  
**Specs validated against:** ADR-001 v1.1 and Phase 0 Milestones v1.1.

## Verdict

**Phase 0 criteria are NOT met. Do not merge this PR as a Phase 0 gate pass.**

The PR title and the committed `gate-results.json` claim a formal gate pass. That claim does not survive independent re-execution. The committed gate run contains ~112 matched pairs — roughly two orders of magnitude below the ≥10⁴ minimum the gate-run protocol requires, a minimum that exists precisely because the 0.5% FMR threshold is statistically meaningless at small n. When the same harness is re-run at any scale ≥200, the gate fails, and the failure worsens with scale:

| Scale (generated pairs) | FMR (threshold ≤ 0.5%) | Recall (≥ 85%) | Gate result |
|---|---|---|---|
| 100 (as committed) | 0.0% | 98.2% | "pass" — sample-size artifact |
| 200 | 1.0% | 98.1% | **FAIL** (FMR) |
| 400 | 3.9% | 95.6% | **FAIL** (FMR) |
| 800 | 5.7% | 93.6% | **FAIL** (FMR + conflict correctness) |
| 2,000 | **15.1%** | 82.3% | **FAIL** (FMR + recall + conflict correctness) |
| 10,000 (protocol minimum) | — | — | **process killed (OOM)** — harness cannot run at required scale |

Consistent across seeds (n=1,000: FMR 7.1% / 8.2% / 7.5% for seeds 7, 99, 12345). The false-match rate *grows* with dataset density: as the generated population thickens, same-merchant/similar-amount records collide inside the tolerance windows and the engine silently matches them. This is exactly the trust-destroying failure mode ADR-001 exists to prevent — at 2,000 pairs, roughly one in seven "matches" silently corrupts a tax record.

## Blocking findings

**B1 — FMR gate failure at scale (above).** Root cause is structural, not tuning: see B4.

**B2 — Determinism fails in fact, and the check cannot detect it.** A 200-iteration probe on the ambiguous scenario produced **four distinct conflict orderings** from identical (input, config). Root causes: conflicts are emitted by iterating Go maps (`for id := range conflictedTxn` in `resolver.go`), and the candidate sort comparator is incomplete (ties on confidence break only by `ReceiptID`, omitting `TransactionID`, under unstable `sort.Slice`). The committed determinism check passes because `resultsEqual` (harness/gate.go) compares conflict **counts only**, never conflict contents or order — a textbook "not actually tested." The CI determinism step (`-count=5`) inherits the same blind spot.

**B3 — Unilateral acceptance-criteria change: duplicate receipts silently tiebroken.** The v1.1 fixture table requires duplicate receipts (forwarded twice) to emit `conflict` — "the engine must not guess which copy is real." `detectTxnAmbiguity` does the opposite by design; its own comment says "duplicate receipts for one transaction tiebreak deterministically," and the committed gate results record `duplicate_receipt: matched=1, conflicts=0`. The handoff protocol states the implementer must never change spec behaviour to make results pass; this change was not routed back.

**B4 — Conflict detection narrowed far below spec, which is the mechanism behind B1.** The spec rule is: competing candidates within the ambiguity margin emit `conflict`, full stop. The implementation adds `signalIndistinguishable`: a conflict fires only if the pair is within margin **and** amount/merchant signals differ by <0.01 **and** temporal deltas are within 60 seconds. Within-margin pairs with different signal mixes therefore silently resolve to the higher score — converting what should be conflicts into matches, many of them false. This single function explains both the FMR blow-up and the conflict-correctness failures at scale.

**B5 — Missing fifth threshold.** `GateThresholds` has no conflict-rate ceiling (≤5% in the v1.1 gate table). The committed report's `overall.conflict_rate` is never computed (always 0), and the per-class value is mis-denominated (ambiguous class reports `conflict_rate: 2`, i.e. 200%).

**B6 — Harness cannot execute the protocol-minimum run.** n=10⁴ is OOM-killed (O(T×R) candidate generation with per-candidate signal maps). The gate cannot be validly run until this is fixed.

## Secondary findings

`go.mod` declares `go 1.25` though the code builds on 1.22 — pin to the lowest working version for portability. The hard-scenario-class list in code (5 classes) differs from the spec's named 2; stricter is welcome but it is an AC change that should be ratified in writing. `EvaluateScenario` applies the hard-class recall floor to every labelled scenario, not only hard classes — also stricter, also unratified. Credit where due: the stdlib-only constraint is honoured (the module builds fully offline), the data model is faithful to D1/D5, the POS exact-ref short-circuit matches D1, the compare mode anticipates Phase 3 measurement, and CI includes race detection and a nightly fuzz workflow.

## Required remediation (ordered)

1. **Resolution correctness (B2/B3/B4):** emit conflicts via sorted, stable iteration; complete the sort key (confidence desc, TransactionID, ReceiptID); remove `signalIndistinguishable` or route its design rationale back to spec review; make duplicate receipts emit `conflict` per the fixture table; add the "equal-confidence candidates never silently resolve" property test; fix `resultsEqual` to compare full conflict contents and order.
2. **FMR at scale (B1):** after (1), re-tune against the gate set under the tuning-log protocol — the conflict-detection fix will convert many false matches to conflicts, which then meets precision at the cost of the conflict-rate ceiling, making the real tuning trade-off visible for the first time.
3. **Harness scale (B6):** index candidates by time bucket/amount band instead of full cross-product; target 10⁵ headroom.
4. **Gate completeness (B5):** add `MaxConflictRate` to thresholds; compute overall conflict rate with a correct denominator; populate seed, config hash, dataset scale, engine version in every report; version the JSON schema.
5. **Missing criteria:** multi-band amount scorer incl. fuel pre-auth; split-tender and refund refusal fixtures; generator distributions, per-class tagging, ambiguous-cluster construction with labels, refund population, DST edges; cohort descriptor corpus + merchant normaliser tests; fuzz targets on normaliser and similarity.
6. Re-run the formal gate at ≥10⁴ pairs on the committed default config and commit the full report.
